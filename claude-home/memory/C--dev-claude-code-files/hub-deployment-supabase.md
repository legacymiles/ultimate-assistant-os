The hub ([[ultimate-assistant-os-portfolio]]) deploys to Vercel project
`ultimate-assistant-os` (team `legacymiles-projects`), live at
**https://ultimate-assistant-os.vercel.app**, from GitHub `legacymiles/ultimate-assistant-os`
(**public** repo — app data is gitignored, but all source is readable).

Supabase project ref **`kiiwaiwrfslqankcsnkf`**
(API URL `https://kiiwaiwrfslqankcsnkf.supabase.co`). The dashboard URL is NOT the
API URL — the user tends to paste the dashboard link; derive the API URL from the ref.

**The site-wide password gate is app-level, not Vercel-level.** The account is on the
**Hobby** plan, where Vercel's Password Protection is Pro-only. It doesn't need it:
`src/middleware.ts` already redirects every unauthenticated request to `/login` whenever
`NEXT_PUBLIC_SUPABASE_URL` + `_ANON_KEY` are set. So **configuring Supabase is what turns
the login wall on** — with those vars empty the whole site is public. Never deploy with
them unset; std-safe holds real health records.

Use the **legacy JWT anon key**, not the newer `sb_publishable_...` key — `@supabase/ssr`
is pinned at 0.5.2. Both authenticate, but the JWT is the compatible one.

**Cross-device sync** for the localStorage apps goes through one table, `public.app_state`
(blob keyed by `user_id` + `key`, RLS-fenced), plus `src/lib/sync/appState.ts` (writes:
local first, then push) and `useSync.ts` (`useRemotePull` pulls at mount). Adding a new
local-first app to sync = export its storage KEY, swap its save for `saveSynced`, and call
`useRemotePull` in its component. Deliberately excluded: **Voice Studio** (base64 audio
belongs in Storage, not a jsonb row) and **Friends Night Out's event cache** (refetchable).

**Deploys are automatic.** `vercel git connect` linked the project to GitHub, so every
push to `main` auto-deploys production (~80s). Do NOT ask the user to run
`vercel deploy` — that command is blocked by the auto-mode classifier anyway, and is no
longer needed. Just push.

**Applying SQL still needs the user.** The schema now lives in `supabase/migrations/`
with a `config.toml`, so `npx supabase db push` works — but only with
`SUPABASE_ACCESS_TOKEN` + `SUPABASE_DB_PASSWORD` in the environment, which Claude does
not have. Absent those, the working method is `Set-Clipboard` the SQL and have the user
paste it into the dashboard SQL Editor; `supabase/all-schemas.sql` (generated by
`scripts/build-all-schemas.sh`) is the full paste-able set.

All 17 tables are applied and verified as of 2026-09-05, including RLS: an anonymous
write to `app_state` is refused (42501) and an anonymous read returns `[]`.

**Every app now persists.** The state that no single viewer owns — std-safe records and
share grants, the Recall Lists board, Recall's password-gate hash, Dance Vault's daily picks —
lives in `public.server_docs` via `src/lib/server/docStore.ts`, and binary files
(std-safe lab reports) via `blobStore.ts`. Both need `SUPABASE_SERVICE_ROLE_KEY` (set as a
Vercel Secret in all 3 envs) because those tables/buckets are RLS-on-with-no-policy, i.e.
deny-all to the publishable key. Both fall back to the filesystem when the key is unset, so
local dev is unchanged — and the key is deliberately NOT in `.env.local`, so local runs do
not read or write real health records.

Voice Studio is the one app that could not use `app_state`: its clips are base64 audio, so
bytes go to the private `voice-clips` bucket (per-user folders, policy-enforced) and only a
path travels in the synced blob. `ClonedVoice.audioDataUrl` is therefore optional.

**PENDING SQL as of 2026-09-07 — the one thing deployed code is waiting on.**
`supabase/migrations/20260906000000_tighten_cross_user_access.sql` is committed and
live in production code but **not applied to the database**. It closes three gaps:
project-files ownership (previously any signed-in user could read/overwrite every
other user's uploads — this is the old "known gap"), and two cookbook share leaks.
It creates `redeem_cookbook_share()` and `cookbook_share_counts()`, which the
deployed Cookbook Genie now CALLS — so until the SQL is run, share-link redemption
and share counts silently return null (they degrade, they do not crash). The
migration is additive, touches no rows, and is safe to run twice. Apply by pasting
it into the Supabase SQL Editor (`Set-Clipboard` the file), since Claude has no
`SUPABASE_ACCESS_TOKEN`/`SUPABASE_DB_PASSWORD`.

**Owner gate (2026-09-19, branch fno-v2-foundation).** Before it, middleware let ANY signed-in Supabase user through the whole hub — and /login offers sign-up, so any stranger could reach STD Safe etc. Now src/lib/hubAccess.ts: only HUB_OWNER_EMAILS reach private apps (fail-closed when unset); /apps/friends-night-out + /api/fno/* are public; non-owners are redirected there (APIs 403). HUB_OWNER_EMAILS must be set in Vercel BEFORE pushing or the owner gets locked out of their own hub.

**Claude cannot see the deployed site.** The login wall means production returns
`/login` to anyone unauthenticated, and entering credentials is off-limits. Verify a
deploy from outside instead: poll `https://ultimate-assistant-os.vercel.app/login`,
pull the `/_next/static/css/*.css` link out of the HTML and grep it for a class name
only the new commit introduces. Confirm state separately with the Vercel MCP
`get_deployment` (project `prj_LJxAg1lpcJtEDzU6K1cG9jzGDvVM`, team
`team_Z1YAZvNkWeLBNrQDpo17V6KA`; ids are in `.vercel/project.json`). A production
push goes READY in about 110s.

**Commit messages: use `git commit -F -` with a bash heredoc.** PowerShell here-string
syntax (`-m @'...'@`) reaches git literally through the Bash tool and lands `@` in the
subject line.
